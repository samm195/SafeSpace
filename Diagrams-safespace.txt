### 1. Integrated Use Case Diagram

This single diagram elegantly replaces the three separate ones by using "Actor Inheritance."

```plantuml
@startuml SafeSpace_Integrated_UseCase
left to right direction
skinparam packageStyle rectangle

actor "Guest" as guest
actor "User" as user
actor "Creator" as creator
actor "Admin" as admin

' Inheritance: Creator and Admin are also Users
user <|-- creator
user <|-- admin

rectangle "SafeSpace System" {
    ' Guest Actions
    guest -- (Register/Login)
    
    ' User Actions
    user -- (Complete Daily Challenges)
    user -- (View Statistics & Titles)
    user -- (Request Creator Status)
    user -- (Read & Like Articles)
    user -- (Browse Volunteering)
    
    ' Creator Actions
    creator -- (Create/Manage Articles)
    creator -- (View Personal Article Stats)
    
    ' Admin Actions
    admin -- (Manage Challenges & Volunteering)
    admin -- (Approve/Reject Creator Requests)
    admin -- (Manage Users & Moderate Content)
    
    ' Includes (Security)
    (Complete Daily Challenges) ..> (Authentication) : <<include>>
    (Create/Manage Articles) ..> (Authentication) : <<include>>
    (Manage Challenges & Volunteering) ..> (Authentication) : <<include>>
}
@enduml
```

### 3. Sequence Diagrams (The 7 Core Flows)

**A. Quest Generation (Daily System)**

```plantuml
@startuml Sequence_Quest_Generation
actor User
boundary Dashboard as "dashboard.php"
control PHP_Engine as "PHP Engine"
database Database

User -> Dashboard : Opens Page
Dashboard -> PHP_Engine : Request Content
PHP_Engine -> Database : Check assignments for today
alt Assignments Exist
    Database --> PHP_Engine : Return existing tasks
else Assignments Missing
    PHP_Engine -> Database : Select 1 random task per category
    Database --> PHP_Engine : Return tasks
    PHP_Engine -> Database : Save to daily_assignments
end
PHP_Engine --> Dashboard : Render Page with Quests
Dashboard --> User : Display Quests
@enduml

```

**B. Quest Completion (AJAX Loop)**

```plantuml
@startuml Sequence_Quest_Completion
actor User
boundary UI as "Dashboard UI"
control JS as "JavaScript (fetch)"
control PHP as "dashboard.php (POST)"
database DB as "Database"

User -> UI : Clicks "Mark as Done"
UI -> JS : completeQuest(id)
JS -> PHP : Send AJAX Request

PHP -> DB : Update status to 'completed'
PHP -> DB : Add +10 XP to User
PHP -> DB : If 1st task today: Streak +1
DB --> PHP : Success

PHP -> PHP : Calculate New Title
PHP --> JS : Return JSON (New XP, Streak, Title)

JS -> UI : Update UI (Animation)
UI --> User : Feedback: "✔ +10 XP Earned"
@enduml

```

**C. Streak Penalty Check (The Brain)**

```plantuml
@startuml Sequence_Streak_Check
participant User
participant PHP as "App_Controller"
participant DB as "Database"

User -> PHP : Logs in
PHP -> DB : Get last_login_date & freezes
DB --> PHP : Returns data

alt User missed days
    PHP -> PHP : Calculate days_missed
    alt Freezes >= days_missed
        PHP -> DB : Deduct Freezes
    else No Freezes left
        PHP -> DB : Set Streak = 0
    end
end

PHP -> DB : Update last_login_date to Today
PHP --> User : Load Dashboard
@enduml

```

**D. Creator Request & Notification**

```plantuml
@startuml Sequence_Creator_Request

PHP -> Mail : Send Notification to Admin
```

```plantuml

@enduml
```

Explanation

1. Integrated Use Case Diagram
Purpose: Defines the functional scope and user hierarchies of the system.

Actor Inheritance: Instead of treating roles as separate silos, we use inheritance. The Creator and Admin inherit all basic User functions (like completing challenges), reducing redundancy.

Key Logic: It visually separates "Public" actions (Guest) from "Protected" actions (User/Admin). The <<include>> relationship specifically highlights that Authentication is a mandatory gateway for the core gamification and management features.

2. Class Diagram (Database Schema)
Purpose: Illustrates the data structure and the relational integrity of the platform.

Normalization: The diagram shows a normalized structure where challenges are separated from user assignments. This allows for a "Pool" of challenges that can be reused daily.

Relationship Mapping: It highlights the One-to-Many relationships (e.g., one user can have many assignments or article likes), which is critical for tracking individual progress and community engagement without duplicating data.

3. Sequence Diagram A: Quest Generation
Purpose: Explains the "Dynamic Engine" that keeps the platform fresh.

Logic: Every time a user accesses the dashboard, the system performs a check. If it's a new day, the PHP Engine fetches 11 random challenges (one from each distinct category) from the database.

Evolution: This ensures the user never sees the same set of tasks two days in a row, automating the variety that keeps the gamification engaging.

4. Sequence Diagram B: Quest Completion (AJAX)
Purpose: Demonstrates the modern User Experience (UX) and backend efficiency.

The "No-Refresh" Loop: Using AJAX (JavaScript fetch), the system updates the database and the user's XP/Streak status in the background.

Feedback Loop: The diagram shows how the server returns a JSON response, which the UI uses to trigger reward animations. This makes the app feel "app-like" and responsive rather than a clunky, old-school website.

5. Sequence Diagram C: Streak Penalty Check
Purpose: Shows the "fairness" logic and the Streak Freeze mechanic.

Automated Maintenance: This flow runs upon login. It compares the current date with the last_login_date.

The Freeze Protection: It highlights the conditional logic where the system prioritizes "Freezes" before resetting a streak to zero, rewarding long-term consistency even if a user misses a day.

6. Sequence Diagram D: Creator Request
Purpose: Outlines the professional verification process.

Document Handling: This covers the file-upload logic. It shows how credentials move from the User’s computer to the Server Storage while the metadata is saved in the Database.

Communication: It includes the Email Notification trigger, ensuring the Admin is alerted to new applications without having to manually check the dashboard constantly.

7. Sequence Diagram E: Article System
Purpose: Highlights the interaction between content creators and consumers.

Role Specificity: It distinguishes between the Creator (who has CRUD permissions) and the User (who has "Read and Like" permissions).

Engagement Tracking: It shows how a "Like" increments the counter in real-time, providing immediate social proof and feedback for the content author.

8. Sequence Diagram F: Admin CRUD
Purpose: Explains how the platform is managed and moderated.

System Control: This illustrates the Admin's ability to manipulate the "Pool" of data (Challenges and Volunteering places).

Security: It emphasizes the Sanitization step—cleaning input before it touches the database—to protect against SQL injection and other vulnerabilities.

9. Sequence Diagram G: Password Reset
Purpose: Demonstrates the security protocols for account recovery.

Token-Based Security: Instead of sending passwords via email, the system generates a Unique Reset Token with an expiration date.

Integrity: The diagram shows the verification step where the token must match the database before the password hash is updated, ensuring the recovery process cannot be easily hijacked.





















Activity diagrams

### 1. Activity Diagram: The Daily Gamification Loop

This represents the absolute core of your application. It tracks the user from login, through the streak/penalty engine, and finally to completing a task.

**Code:**

```plantuml
@startuml Activity_Daily_Gamification
skinparam ActivityBackgroundColor #fce4ec
skinparam ActivityBorderColor #fd79a8
skinparam ArrowColor #6c5ce7

|User|
start
:Log into SafeSpace;

|System Backend|
:Fetch User Data (last_check_date, freezes, streak);
if (Missed previous day(s)?) then (Yes)
  if (Available Freezes >= Days Missed?) then (Yes)
    :Deduct Freeze(s);
    :Maintain Streak;
  else (No)
    :Reset Streak to 0;
  endif
else (No)
  :Maintain Streak;
endif
:Update last_check_date to Today;

:Check daily_assignments table for Today;
if (Assignments exist for Today?) then (No)
  :Fetch 11 random challenges (1 per category);
  :Generate new daily_assignments rows;
else (Yes)
endif
:Render Dashboard UI;

|User|
:View Daily Challenges;
:Complete real-life task;
:Click "Mark as Done";

|System Backend|
:Update assignment status to 'completed';
:Add +10 XP to User profile;
if (First task completed today?) then (Yes)
  :Increment Streak by 1;
else (No)
endif
:Calculate if New Title is unlocked;
:Return updated stats via JSON (AJAX);

|User|
:See UI update (XP bar fills, checkmark appears);
stop
@enduml

```

**Explanation for your report:**

> **Purpose:** This diagram maps the primary user journey and the automated gamification engine.
> **Logic Flow:** By utilizing swimlanes, it clearly separates the frontend User actions from the automated Backend System processes. It visually demonstrates the complexity of the "Penalty Check" (verifying missing days and applying Streak Freezes) occurring instantly upon login before the user ever sees their dashboard. It also illustrates the asynchronous (AJAX) loop of claiming XP without interrupting the user experience.

This diagram maps the workflow that crosses between three distinct entities: The User, the System, and the Admin. It perfectly covers Requirement 4.1 & 4.6.

```plantuml
@startuml Activity_Creator_Approval
skinparam ActivityBackgroundColor #fce4ec

|User|
start
:Navigate to "Request Creator" page;
:Upload professional credentials (PDF/Image);
:Submit Application;

|System Backend|
:Validate file size and extension;
:Save file to secure storage;
:Create record in creator_requests (status: 'pending');
:Trigger Email Notification to Admin;

|User|
:Receive "Application Submitted" confirmation;

|Admin|
:Log into Admin Panel;
:Open "Pending Requests" module;
:Review User Credentials document;

  :Update request status to 'approved';
  :Change User Role from 'user' to 'creator';

  |System Backend|

|Admin|
:Proceed to next task or Exit;
stop

```

**Explanation for your report:**

> **Purpose:** This diagram outlines the administrative workflow for verifying mental health professionals and content creators.
> **Logic Flow:** The swimlanes illustrate the handover of responsibility. The User initiates the process, the System handles the file validation and automated notification, and the Admin provides the final human-decision step. It highlights the platform's role-based access control (RBAC) by showing exactly when and how a standard user is elevated to a Creator.
